# Taomni 新功能设计

把新增或扩展能力的需求转成其他 agent 无需当前聊天历史即可实施、测试和真机验证的设计。默认中文，保留代码标识符原文。设计重点是用户行为、现有能力复用、共享契约和可验收的工作包。

## 入口与自然语言路由

`prompt`、`design` 是消息中的模式词，不是终端命令；均可省略。

| 请求 | 行为 | 读取资源 |
|---|---|---|
| `$feature-design prompt [功能描述]`，或“帮我生成新功能设计的提示词” | 输出可复制的定制提示词 | [提示词范本](references/prompt-template.md) |
| `$feature-design design <需求或已有功能设计>`，或“设计一个……功能”“细化这份功能文档” | 调研代码并落盘详细设计 | [设计工作流](references/detailed-design.md)、[文档模板](assets/design-document.md)；写验证部分时读取[验证设计](references/verification.md) |

未写模式但提供了具体功能时默认 `design`；明确要求提示词或范本时优先 `prompt`。只调用 skill 而没有主题时给可填的提示词范本。issue 编号只是来源，若其内容是新增需求，仍属于功能设计。

`prompt` 返回提示词后结束，不执行其中的设计任务。`design` 默认交付设计文档；用户同时要求实现或验证时，继续已经授权的工作，不额外设置设计审批关卡。

## 固定前提

- 读取当前 Taomni 工程适用的 `AGENTS.md`，使用工程相对路径，不硬编码某台机器的检出位置。
- 产品固定为 Windows、macOS、Linux 三端 Tauri 桌面应用，方案与代码必须兼容三端构建和运行。提示词直接声明，不提供平台或 desktop/browser 选项。浏览器用于开发和辅助测试。
- 真机计划覆盖三端，本轮完成当前运行端真机验证即可满足本轮真机交付条件。其他端保留未验证及后续步骤，不因缺少设备阻塞本轮交付；已知代码不兼容仍须解决。
- 现状以当前代码、配置和实际观测为依据，历史文档提供背景。明确区分事实、推断、拟新增内容和待验证假设。
- 普通实现选择由 agent 作出有依据的决定；设计中的实质取舍按下节邀请用户参与，需求描述完整也不代表方案取舍已经确定。

## 设计中的人工决策

先核对当前会话、已有设计中的有效决定和明确的代决授权。已确定的偏好直接沿用；用户明确要求 agent 自行决定时，在授权范围内选择并记录理由。只有新证据使原决定不再适用或超出授权边界时，才说明变化并重新提出。

调研中主动识别以下取舍。存在多个合理方向，且现有要求、工程惯例或技术证据不能决定用户偏好时，在细化依赖它的方案前邀请用户决策：

| 决策类型 | 需要人工参与的情况 |
|---|---|
| UI/UX | 新入口、信息组织、主要操作流程、默认行为、反馈与恢复方式存在明显不同的使用体验，例如侧栏与独立页面影响上下文保留和工作空间。 |
| 组件与技术选型 | 复用、引入或替换组件/依赖会明显影响交互能力、可访问性、性能、包体、许可证、长期维护或替换成本，需要取舍。先由 agent 核实候选是否满足三端及现有架构约束。 |
| 范围与优先级 | 简单性与可配置性、交付范围与成本、性能与资源占用、兼容性与迁移代价不能同时满足，需要用户明确优先级或接受行为变化。 |

局部实现细节、沿用成熟组件且体验不变、已有契约唯一确定的行为由 agent 自主处理。缺少技术事实时先调研或安排最小验证，不把可查证问题交给用户猜测；没有实质取舍时无需凑选项或固定提问轮数。

发现影响需求边界的问题时尽早提出；方案取舍则先形成足以比较的候选，在写死交互、共享契约和任务依赖前提出。后续发现新的实质取舍时再次判断，不把全部问题留到文档末尾。

每轮聚焦当前最影响后续工作的少量决策（通常 1–3 个）：说明当前依据、为何需要用户判断、通常 2–3 个可行选项及其用户体验/工程成本、推荐项与理由，以及影响的范围。UI/UX 按下节展示原型与示意图；组件选型用能力与成本比较，不只列库名。支持用户提出替代方案，不用泛泛的“是否确认设计”代替具体选择。

按当前环境允许的交互方式实际提出问题；支持异步提问时可边等回复边推进独立调研和设计，不能只在文档里列“待确认”。需要用户决定的部分可写条件性草案，依赖任务保持待决；未回复、超时或推荐项被预选都不代表同意。收到答复后更新相关行为、契约、AC、TASK 和 V；用户明确授权代决时按其边界收敛。没有可继续的独立工作时，交付已完成部分并明确待决问题及受影响任务。

在设计内用稳定 `DEC-*` 记录有实质影响的决定：问题、选项与代价、结论、理由、状态（用户已定 / 授权代决 / agent 自决 / 待用户决策）、来源（用户答复摘要、授权范围或代码依据）及关联 AC/TASK/V。仅保留推荐的待决项不得写成用户已定；修订保留原 ID 和变更原因。这是按需参与设计，不新增逐步审批或文档最终审批关卡。

### 原型与示意图的交互决策

原型/示意图本身也是需要用户反馈的设计对象。涉及新界面、布局、信息结构或主要交互流程调整，或用户要求看原型时，在 UI 方案定稿前提供可查看的图稿或原型并邀请用户针对它决策；纯内部功能或不改变结构/流程的简单 UI 修正按影响处理，不强制制作整套原型。已有图稿决定和明确代决授权仍按上述规则沿用。

先制作足以判断本轮问题的低成本示意图、线框或交互原型，展示真实入口、布局与关键状态；有实质备选时提供可比较的版本。静态图不能表达决定性的操作反馈时，再补最小可交互原型。示意图按当前环境可用的 `drawio` skill 生成，提供可编辑产物和可直接查看的预览；工具不可用时采用可用的本地可视化方式并说明局限，不能把只有文字描述当作已交付图稿。

实际展示图像或可访问的原型链接，标明方案/版本、关键状态及适用窗口尺寸，先检查渲染、可读性和明显遮挡。提问指向具体图稿和选择，例如布局 A/B、入口位置、信息密度、关闭/恢复流程，附推荐与影响；不要只在文档附图后结束。根据反馈修订并展示差异；影响原有决定的实质变化再次邀请用户判断，普通细节修订自主完成。

在 `DEC-*` 关联图稿路径/版本、反馈摘要、采纳或未采纳理由、最终选择或待决状态。图稿默认放在 `docs-feature/<feature-slug>/`，文档用相对链接引用并标清当前有效版本；图稿、文字、交互状态和 AC/TASK/V 保持一致。图稿生成、截图成功或用户选择均不等于产品已实现、UI 测试通过或真实桌面验证完成。

## 文档位置与交接

默认输出工程根目录下的 `docs-feature/<feature-slug>-design.md`，目录不存在时创建。先检查同名文档，再复用或选择明确的新名称。

细化 `docs-feature/` 中的文档时原位更新，保留有效决策、ID 和证据。输入文档位于其他目录时默认作为资料，在 `docs-feature/` 产出并记录来源，保留原文；用户明确指定其他输出位置时遵从。不要批量迁移历史文档。

使用稳定的验收 `AC-*`、任务 `TASK-*`、验证 `V-*` ID 串联方案和证据，沿用已有编号。设计要写清行为、代码落点、接口与状态、任务文件职责和依赖、测试断言、三端适配及当前端真机步骤；按变更规模合并章节，但不能将关键决定留给接手 agent 猜测。

设计状态“可实施”不表示实现或验证完成。拟执行检查初始标为待执行，实际观测另附命令、环境和证据。任务拆分不自动授权启动多个 agent 或修改任务看板。

最终返回文档链接、主要方案、关键决策状态、可开始的任务及确实存在的阻塞。设计文档应自包含，下游不必安装本 skill 才能执行。
