# 测试与真机验证设计

本文件指导设计验证方案，不要求设计阶段执行全套测试。若为确认现有行为运行了检查或测试，另行记录实际结果；实现后的验收仍保留独立待执行条目。

## 按证明目标选层级

| 层级 | 适合证明 | 在设计中落实 |
|---|---|---|
| Vitest | 纯逻辑、store、组件可观察行为、相关异步边界 | 现有或拟新增测试文件、输入/动作/断言、需要隔离的依赖 |
| Rust unit | 后端算法、状态机、错误和资源生命周期 | 模块路径、inline tests、筛选命令 |
| Rust integration | 多模块协作、真实 IPC 后的核心处理或测试依赖交互 | 核对 `src-tauri/tests/README.md`；现有集成套件通常在 `tests/integration/` 单一 binary 中 |
| 浏览器 UI | 页面入口、操作结果、可见反馈及可在此环境观测的状态变化 | feature/case/selector 映射、fixtures、操作与断言、stub 或真实桥接边界 |
| 原生真机 | Tauri WebView + Rust 调用链、实际系统行为、真实依赖互操作 | 目标平台、被测应用、前置条件、运行步骤、系统副作用与证据 |

各层级按影响选择，不要求每个小改动都写满所有层。真机计划固定覆盖 Windows、macOS、Linux 三端 Tauri 桌面，至少为受影响主流程安排原生 smoke；即使只是 UI 变化，也应在真实 WebView 中验证。本轮在当前运行端完成这些真机验证即可，其他端未执行时保留“未验证”及接续步骤。浏览器模式只承担辅助测试。

三端代码兼容检查是本轮工作：审查受影响的条件编译、依赖、平台 API 及适配分支，并执行当前环境可用的相关编译和测试。其他端缺少构建或真机环境时记录检查依据及未实测范围；不能把已知的其他端编译错误或运行缺陷归为“缺少设备”后放行。当前端通过也不能证明其他端已实测通过。

每个 `V-*` 写明前置状态、数据或输入、触发步骤、预期结果、适用 `AC-*`、执行方式与所需产物。新功能测试应证明新增的用户行为和副作用，并包含受影响的既有功能回归；若难以自动化，提供确定的手工步骤与断言。避免仅检查内部调用次数、控件存在或截图生成，而没有业务结果断言。

覆盖与变更有关的正常、边界、失败及恢复场景，并选择最可能受影响的相邻功能回归。不要为无关功能扩展整套质量工程。

## 命令要能执行

从当前 `package.json`、`Cargo.toml`、测试文件和 runner 的帮助中核对命令与筛选条件。写明工作目录、shell、必要环境变量名称；未新增的测试路径和用例 ID 标为实现后使用。不要给出不存在的脚本或把伪参数写成现成命令。

仓库常用入口（生成文档时仍需核对）：

- 仓库根目录：`pnpm test <相关测试文件>`；`pnpm build` 检查类型与前端构建。
- `src-tauri/`：`cargo test --lib <模块过滤>`；需要集成时 `cargo test --test integration <过滤>`。
- 仓库根目录：`pnpm dev` 启动浏览器开发模式；`pnpm tauri dev` 启动真实桌面开发模式。浏览器构建通过不能证明原生编译或运行成功。
- 涉及打包资源、权限、启动或发布行为时增加打包应用验证；确切构建命令与运行入口以当前配置和平台 runbook 为准。

PowerShell 环境变量用 `$env:NAME = "value"`，不要复制 Bash 的前置赋值语法。凭据仅引用环境变量名称；测试应使用独立 app-data、工作目录和测试数据，给出复原步骤，不清空开发者配置。

活体服务测试可能被 ignore、缺少变量而提前返回或跳过。设计中要求验证实际选中的 case、执行数和 skip 原因，不能仅凭命令退出码 0 判定真实路径已覆盖。

## UI 自动化的仓库对接

涉及 UI 时，读取相关 `feature-list.md` 条目和现有 case。需要给出具体 YAML 草案、selector 或 runner 方案时，先读仓库 `.agents/skills/qa-ui-auto/SKILL.md`，按需读其 `references/authoring.md`、`verb-catalog.md` 和 schema。

在设计中给出已存在的 feature ID、case 文件和 `data-testid`，或明确标注拟新增内容。新的 `covers` / `controls` / case 编号需与当前目录去重，不能假称已登记。将必要的目录维护、selector 变更和测试更新分配给实现任务；生成目录应使用当前工具更新。

现有 qa-ui-auto 主要覆盖功能与控件行为。视觉布局、可访问性、性能等若属于本次 AC，安排对应测量或手工验收，不能从功能覆盖率推导其通过。

## 真机验证必须具体

每份设计应列出以下与本次相关的内容：

1. 分别列出 Windows、macOS、Linux 的系统、架构、WebView 和被测应用来源，区分原生开发运行与打包应用。标明自动识别的当前运行端及本轮执行项，其他端保留验证计划，平台范围无需用户选择。
2. 所需真实服务、设备、provider、账号权限、版本或测试数据，以及如何确认后端与依赖确实就绪。用安全的测试资源引用代替凭据值。
3. 通过真实 UI 触发主流程，逐步说明可见结果与真实系统副作用，例如落盘内容、远端状态、进程退出或权限反馈。纯原生 backend 测试不能独自替代桌面主流程。
4. 与本变更有关的失败/拒绝/中断、恢复，以及必要的关闭重开或重启验证；每步有明确预期。
5. 收集的命令、日志、截图或录屏、结果数据与来源标识，以及测试数据和进程的清理方式。清理范围限本轮测试资源。
6. 无法执行的环境写明缺少什么、影响哪些 AC、由谁或哪类环境接续以及可执行的替代路径。其他端缺少环境不阻塞当前端验证完成后的本轮交付。当前端自动化不可用时可用手工真机验证；设计阶段仍是待执行，当前端实际验证缺失或失败不能记为本轮真机完成。

复用 `qa-ui-auto-tests/native/` 前先读其说明及选用的 runbook/collector；其中有 Code Workspace 专用门禁和字段，不自动推广到其他功能。文件存在不代表该平台脚本可运行，应核对 runner、驱动和 case 的真实支持。现有工具不能覆盖时设计手工步骤或必要的自动化改动，不编造可运行命令。

`pnpm dev` + Playwright、browser stub、synthetic fixture 或 mocked provider 均不能替代真实 Tauri 后端及真实服务的证据。即使浏览器桥接接触了真实服务，也应准确标注仍未覆盖的原生层。每个平台独立记录结果；不从一个系统推导另一个系统通过。

## 证据与完成条件

为本次选择适度的证据字段：AC/V ID、代码提交及相关未提交变更、被测构建标识、环境、执行命令或手工步骤、时间、实际结果、产物路径、未覆盖项。打包或版本敏感问题应保存二进制路径和 hash；使用现有证据框架时遵守其字段与生成方式，不新造签名或门禁系统。

原始截图与日志可放 `qa-ui-auto-report/` 的专题目录，遵守 gitignore；文档保留脱敏摘要与路径，面向其他机器交接时说明如何获得产物。不能直接修改自动生成的 manifest 来把待验证项写成通过。

计划中写“待执行”；实际执行后区分“通过 / 失败 / 环境阻塞 / 未验证 / 不适用（具体场景及理由）”。三端桌面整体不能因缺少设备标为不适用。

本轮交付条件包括三端代码兼容检查、本轮必要的自动化检查和当前运行端真机验证。满足后可以报告本轮完成，同时逐端列出其他端未验证的范围与后续计划；这些未执行项不单独阻塞本轮交付。已知代码不兼容、本轮必要检查失败或当前端真机验证未完成，仍是本轮缺口。只有三端均有实际通过证据时才能报告“三端真机验证通过”。
