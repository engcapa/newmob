# 功能设计提示词

`prompt` 模式返回一个可复制的提示词代码块。将用户提供的信息代入下方范本，去掉无关可选字段；没有主题时保留待填项。未提供的事实不能补造，也不用为了生成范本扫描业务源码或运行测试。

生成的提示词可以用 `$feature-design design`，也可以写 `$feature-design 请为……编写详细设计`。两者效果相同。固定保留三端桌面兼容与当前端真机完成规则，不生成平台选择题。

```text
使用 $feature-design design 为 Taomni 设计以下新功能，并将详细设计写入工程 docs-feature/。

功能名称：[名称]
用户与问题：[谁在什么场景中需要什么结果]
核心流程：[入口 → 操作 → 可观察结果；不确定的部分由你提出方案]
必须包含：[本次功能范围]
不在范围：[可选]
性能、数据兼容或其他约束：[可选]
参考资料：[现有设计、需求 issue、相关模块或截图描述；可选]

平台固定为 Windows、macOS、Linux 三端 Tauri 桌面应用，方案和代码必须兼容三端构建与运行。
真机验证计划覆盖三端，本轮在当前运行端完成真机验证即可；其他端记录未验证及后续步骤，不因缺少设备阻塞本轮交付。

读取适用 AGENTS.md，定位现有入口、组件、状态、IPC、Rust 模块和相关测试，依据当前代码决定复用和改动。
普通实现选择由你完成；会改变产品行为或关键验收的缺口请提出具体问题，同时推进独立部分。

文档应让另一位没有当前聊天历史的 agent 能实施和验证：

- 写清目标、范围和带 AC ID 的可观察验收条件。
- 详细设计用户流程、相关交互状态、数据归属、接口类型、持久化、异常恢复和三端适配。
- 列出准确代码落点，标注拟新增文件和符号，说明关键选择及理由。
- 拆分带文件职责、依赖、实施要点、验收 ID、验证项与完成条件的任务，并安排集成责任。
- 给出有输入和结果断言的自动化测试，以及三端真机计划和当前端的具体操作、真实依赖、证据与清理步骤。
- 建立 AC → 方案 → 任务 → 验证 → 证据的对应关系，列出风险和未决项，所有计划检查初始标为待执行。

默认输出 docs-feature/<feature-slug>-design.md。本次交付设计文档，完成后返回路径与主要结论。
```

细化已有功能设计时，把开头改为“使用 $feature-design 细化 [来源路径]，保留有效决策、ID 和证据，补齐开发、测试和真机交接信息”。默认仍输出 `docs-feature/`，该目录内已有目标则原位更新。用户明确要求后续实现时，保留授权，不加入范本中的“本次交付设计文档”限制。
