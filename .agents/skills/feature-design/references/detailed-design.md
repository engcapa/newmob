# 功能详细设计工作流

结合 [文档模板](../assets/design-document.md) 产出 `docs-feature/<feature-slug>-design.md`。模板中的提示由 agent 调研和设计，不是逐项询问用户的清单。

## 1. 明确需求与现有能力

读取适用 `AGENTS.md`，记录当前提交和相关未提交变更。识别目标用户、触发场景、当前限制、预期结果和本次边界；不要自动领取 backlog 任务。

从用户入口追踪调用链，按需检查：

| 事实 | 仓库调研入口（以当前代码为准） |
|---|---|
| UI、布局和事件 | `src/components/`、`src/layouts/` |
| 状态来源与恢复 | `src/stores/` 及调用者 |
| IPC、返回值与事件 | `src/lib/`、前端调用点、Rust command 定义与注册 |
| 真实副作用和存储 | `src-tauri/src/`，相关配置与 capability |
| 浏览器辅助路径 | `src/stubs/`、`vite.config.ts`；有真实桥接时再读 `vite-plugins/` |
| 既有测试和设计 | 相邻 Vitest/Rust 测试、`src-tauri/tests/README.md`、相关 `docs-feature/`、`docs-issue/`、历史 `claudedocs/` 文档 |
| UI 验证设施 | 相关 `qa-ui-auto-tests/feature-list.md` 条目、YAML cases；按需查看 native runner |

用“工程相对路径 + 符号名 + 必要行号”记录依据，区分现有能力、可复用部分和拟新增对象。需求 issue 可访问时读取相关内容；缺少访问权限时使用用户已有描述，注明无法核实部分。

核对用户已有决定和代决范围，识别会改变调研方向的目标、范围或体验偏好缺口并尽早提出。按 [人工决策规则](../SKILL.md#设计中的人工决策) 区分可由证据解决的问题和需要用户取舍的问题；技术不确定性先查证。

## 2. 定义行为与契约

将目标变为可观察的 `AC-*`：明确前置条件、动作和结果，包含相关失败、恢复与兼容场景。“支持某功能”“测试通过”不能独自作为验收。性能敏感需求写明负载、指标、计时边界和目标来源；无基线时安排测量，不虚构数字或通过结果。

在细化契约前检查 UI/UX、组件选型及范围/成本取舍。有需要用户选择的事项时，先展示具体候选、影响和推荐并实际提问；将结论或待决状态写入 `DEC-*`。回复前继续独立部分，相关方案和验收仅标为条件性草案。简单方案不强凑备选。

涉及新界面、布局/信息结构或主要流程调整，或用户要求原型时，按 [原型交互规则](../SKILL.md#原型与示意图的交互决策) 先制作并展示图稿/原型，再围绕具体版本收集选择与反馈。按反馈修订并展示差异，将当前有效图稿和反馈关联 DEC；不能只在最终文档附图而省略人工交互，已有决定与代决授权按规则沿用。

依据已确定或授权代决的方向，写清下游必须共享的决定；后续出现新取舍时回到上述交互：

- UI 入口、主流程、文案和控件行为，相关加载、空内容、错误、禁用、快捷键、焦点、关闭与恢复状态。
- 权威状态、派生状态、持久化字段与读写时机，跨窗口或重启后的语义。
- 新增或变更的接口名称、TS/Rust 类型、序列化字段、默认/可空值、返回值、错误；有事件时写 payload、顺序和订阅释放。
- 后台资源和副作用由谁创建、持有和释放；相关的取消、超时、去重、幂等、过期响应或并发冲突。
- 涉及数据格式变更时的旧数据读取、迁移触发、失败和回退边界。
- Windows、macOS、Linux 的受影响条件编译、依赖、系统 API、路径、权限和 WebView 适配。平台特有能力须有满足需求的适配或降级，三端均应可构建、启动和正常运行。
- 浏览器 shim 的辅助测试范围与必须真实 Tauri 验证的行为。

按需要给签名、字段表、状态转换或短伪代码，不预写完整实现，也不以“加接口”“做好错误处理”替代设计。

## 3. 形成可实施工作包

列出准确改动路径与符号，标注拟新增内容，并将其分配到 `TASK-*`。每个任务有目标、文件职责、输入与必读材料、依赖、具体改动、对应 AC/V 和完成条件。依赖人工决策的任务关联 `DEC-*` 及解除条件，明确哪些任务可开始、哪些须等待。

明确共享文件归属、可独立的任务和必须等待的契约。安排整体集成、相邻功能回归、三端兼容检查、当前端真机验证及文档回填的责任。用职责名称，不假称 agent 已领取或已执行。

保留其他执行者的工作，协调重叠改动；任务拆分本身不授权启动子 agent 或变更共享看板。现有模块有编号体系时关联并去重。

## 4. 设计测试与交付

读取 [验证设计](verification.md)，把要求落实为具体测试文件、case、输入/动作/结果断言、命令、环境、证据和 `V-*`。选择能观察用户结果和真实副作用的验证，明确浏览器 stub、真实后端及外部服务的证明范围。

真机计划包含三端，当前端由环境识别。本轮完成条件包含三端代码兼容检查、必要自动化和当前端真机验证；其他端未执行保留计划与未验证状态，不因设备缺失阻塞本轮交付。设计阶段只制定计划，不能声称验证已完成。

文档应自包含具体步骤。可引用工程已有 runner/runbook，但核实其能力，并写明选用 case 和对应 AC；拟新增的测试或自动化能力要分配实现任务。

## 5. 审查与落盘

逐条检查 `AC → 方案 → TASK → V → 所需证据` 是否完整。走通主流程和本次最重要的异常分支，核对状态、契约与任务之间无冲突。抽查文件、符号、命令、testid/case 是否存在；新对象明确标为计划。

核对 `DEC-*` 的结论与来源，确保用户答复已同步到方案、AC/TASK/V，推荐未被误记为用户决定。涉及 UI/UX 或选型时能说明为什么需要人工参与，或为何按现有要求/授权自主决定；无需为了审查再发起一轮确认。

涉及原型时核对预览可查看、有效版本明确、反馈及处理结果可追踪，且与文字和验收一致；未经实际展示的图稿不能记为已收集用户反馈，原型评审不能充当 UI 或真机测试结果。

删除未替换的模板提示及不适用空章节。保留必要未决项，并说明影响、建议、解除条件及具体受阻任务；完成独立设计。待用户决策影响的部分保持草案或部分可实施；只有必要决策已收敛、验收和关键契约足够清楚时才标为可实施，且不等于实现完成。

按入口约定在 `docs-feature/` 新建或细化设计，保留有效 ID 和证据，引用外部目录来源而不擅自覆盖原文。返回文档路径、推荐方案与能开始的工作。
