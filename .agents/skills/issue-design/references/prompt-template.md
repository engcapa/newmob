# Issue 修复设计提示词

`prompt` 模式返回一个可复制的提示词代码块，填入已有问题信息并删除无关可选项。没有问题主题时保留待填字段；未知频率、版本、复现结果和根因如实留空或标未知，不能补成事实。生成范本不提前执行诊断、设计或修复。

可用 `$issue-design design` 或自然语言 `$issue-design 请为……编写修复设计`。固定保留三端桌面兼容与当前端真机完成规则，发生环境只是复现信息，不是平台选择。

```text
使用 $issue-design design 为以下 Taomni 问题编写可实施的修复设计，输出到工程 docs-issue/。

问题或 issue：[编号、地址或完整问题描述]
预期行为：[应当发生什么]
实际行为与影响：[发生了什么，影响哪些操作或数据]
复现步骤和频率：[已有信息；未知请写未知]
问题发生环境：[已知系统、应用版本或提交、相关服务版本；可选，仅用于复现]
证据：[日志、错误、截图描述、失败测试；可选，排除凭据]
修复约束：[必须保持的行为、数据格式或接口兼容要求；可选]
参考资料：[已有修复设计或相关模块；可选]

产品固定为 Windows、macOS、Linux 三端 Tauri 桌面，修复代码必须保持三端构建与运行兼容。
真机验证计划覆盖三端，本轮完成当前运行端验证即可；其他端记录未验证及后续步骤，不因缺少设备阻塞本轮交付。

读取适用 AGENTS.md，追踪当前代码中的触发条件、执行路径、不变量破坏与用户可见结果。
区分复现事实、静态证据和根因假设；不能复现时记录已检查内容、缺失条件和能区分候选原因的最小验证。
主动识别预期行为、修复 UI/UX、组件替换、兼容代价与修复范围的实质取舍，在固定依赖契约前邀请我参与需要偏好或优先级判断的决定；根因仍由技术证据判断。
先调研，再给出候选修复、恢复/改变的行为、剩余风险与成本、推荐及理由，每轮聚焦少量关键问题；沿用我已有决定，恢复明确既有行为的普通实现选择由你完成。
修复涉及布局、主要流程或错误恢复交互的实质变化时，先提供可查看的修复前后原型/示意图，针对具体图稿版本邀请我选择或反馈；据此修订并展示差异，再收敛 UI 修复方案。区分真实问题截图和拟议图，不只在最终文档附图。
需要我决定时实际提问，等待期间推进独立诊断和设计，依赖方案保持条件性草案；未回复不等于同意。若我明确授权你代决，按授权范围选择并记录。

文档应交接给其他 agent 实现、测试和真机复测，包含：

- 原问题依据、根因确定性、修复范围及必须保持的相邻行为。
- 带 AC ID 的修复后可观察结果，以及修复前失败、修复后通过的回归场景。
- 与因果链对应的修复方案、理由、准确文件和符号、相关接口/状态/数据变更及三端兼容处理。
- 涉及原型时交付可查看的预览与可编辑产物，记录图稿路径/版本、人工反馈及处理结果，并与修复契约及验收保持一致。
- 用 DEC ID 记录重要选项与代价、结论、理由、状态（用户已定/授权代决/agent 自决/待用户决策）、来源及关联 AC/TASK/V；收到答复后同步更新，标清待决项影响的任务。
- 有文件职责、依赖、实施要点、AC/V ID、完成条件的工作包，包含回归与集成责任。
- 具体测试输入、动作、断言、命令及前置依赖；三端真机计划和当前端的复测、证据、清理步骤。
- AC → 方案 → 任务 → 验证 → 证据对应关系，风险、必要回退及未决项影响。未执行验证标为待执行。

默认输出 docs-issue/<issue-id-or-slug>-design.md。本次交付设计文档，返回路径、根因确定性和推荐修复。
```

细化已有修复设计时，将开头改为“使用 $issue-design 细化 [来源路径]，保留有效结论、ID 和证据，补齐实现、回归及真机复测信息”。默认仍输出 `docs-issue/`，该目录内已有目标则原位更新。用户同时授权后续实现时保留授权，不加入范本中的“本次交付设计文档”限制。
