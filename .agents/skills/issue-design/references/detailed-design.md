# Issue 详细修复设计工作流

结合 [文档模板](../assets/design-document.md) 产出 `docs-issue/<issue-id-or-slug>-design.md`。以问题证据决定修复，模板中的提示由 agent 调研，不是要求用户提供完整诊断材料。

## 1. 固定问题边界与基线

读取适用 `AGENTS.md`，记录提交、相关未提交变更、已知发生环境及当前执行环境。产品兼容范围固定三端桌面，不让用户重新选择平台。

明确预期与实际、复现步骤、频率、影响对象、已知正常场景和既有 workaround。issue 可访问时读正文及影响结论的讨论，无法访问时用已有描述推进并注明缺口。相关提交历史用于定位回归时机，不能独自证明根因。

沿入口追踪相关 `src/components/`、`src/layouts/`、`src/stores/`、`src/lib/` 和 `src-tauri/src/`，核对 IPC 注册、配置及实际副作用。浏览器材料需检查 `src/stubs/`、`vite.config.ts` 和相关桥接，确认是否经过真实 Rust。阅读相邻测试、`src-tauri/tests/README.md` 及相关 `docs-issue/`、`docs-feature/` 或历史 `claudedocs/` 资料。

用工程相对路径、符号和必要行号记录现状。区分源码事实、历史文档描述和实际复现结果；不把旧文档的“已完成”当证据。

## 2. 建立可验证因果链

描述“触发条件 → 当前执行路径 → 被破坏的不变量 → 用户结果”。对关键边界说明调用方、状态拥有者和副作用位置，判断修复应落在哪层，避免只隐藏可见症状。

复现步骤应包含环境、初始数据、具体输入、动作、预期与实际、证据位置。适合且在范围内时可以进行必要诊断；没有实际执行就标待执行。不得为了完成设计清理真实用户配置或修改产品代码。

若根因还存在多个解释，列出各自支持与反证、能区分它们的最小测试及所需环境；不要求凑候选数量。将确认根因的工作做成具体诊断任务，修复任务注明成立条件，继续完成独立的接口分析、回归设计和交接。

## 3. 设计修复及回归契约

给每个必须恢复或保持的行为稳定 `AC-*`，包含具体前置、触发和结果。至少有一个场景能在原实现暴露本问题、在修复后验证正确；相关并发、取消、失败恢复或跨平台边界按因果关系选取。

推荐修复应逐项对应根因，说明代码落点、选择理由、对正常行为的影响及必要的备选。避免把重构相邻模块或增加新功能作为没有依据的修复前置。

对受影响契约写到下游可直接实现的粒度：

- UI 和状态：失败反馈、加载/禁用、焦点、退出恢复，以及状态权威来源、异步时序、取消和旧响应处理。
- 接口：准确函数/IPC/事件名、TS/Rust 类型及序列化、可空/默认值、返回/错误语义、订阅释放；不变契约注明沿用。
- 真实副作用：写盘、网络、进程等执行边界、资源生命周期、失败后的数据与恢复行为。
- 数据变更：确有必要时说明迁移、旧数据兼容、失败与代码/数据回退边界。
- 三端兼容：受影响的 Rust `cfg`、依赖、平台 API、路径、权限和 WebView 分支；平台特有能力有适配或符合要求的降级，不能破坏其他端构建和运行。
- 浏览器辅助测试：shim 的行为与真实原生链路的区别。

使用必要的签名、字段表、状态转换或短伪代码，不预写全部实现。已有失败测试只证明问题时，应补充修复后正确行为与相邻行为保持的断言。

## 4. 交接实现与验证

列出文件和符号级改动清单，标注拟新增对象并分配 `TASK-*`。每个工作包写清目标、文件职责、输入/必读材料、前置任务或契约、具体改动、AC/V、完成条件。需要时先安排诊断或回归用例，再实施修复，最后集成和复测。

指定共享文件归属和协调责任，保留其他执行者改动；安排相邻回归、三端兼容检查、当前端真机及证据回填。不要假称 agent 已领取任务，拆任务不自动授权启动子 agent 或修改看板。

读取 [验证设计](verification.md)，将其落实到 `V-*`、文件/case、输入/动作/断言、实际命令、工作目录、环境、真实依赖及产物。写清原问题的失败点、修复后的通过条件和 mock/stub 的证明范围。

真机计划列三端，本轮在当前端执行必要真机流程即可。若原 issue 只在其他端发生，明确当前端验证的是兼容/相邻流程，原始触发场景仍未验证并留下接续步骤；不将其声称为原平台已复现并修复。缺少其他端设备不单独阻塞本轮交付，已知代码不兼容仍须解决。

## 5. 审查设计并落盘

核对每条 AC 都有方案、负责的 TASK、V 与所需证据；复现、根因与修复之间的逻辑不能断裂。核实引用文件、符号、测试 ID、selector 和命令，标清拟新增内容。

按主流程和关键故障路径走一遍，检查时序、数据和接口决定是否矛盾。删掉空表、未替换模板提示及无关章节，保留必要未决项的影响、建议、最小检查、解除条件和具体受阻任务。

根因有充分依据且契约明确时标为可实施；依据不足则标草案或部分可实施并交接诊断任务。设计状态不代表修复和验证已完成。按入口约定在 `docs-issue/` 落盘，保留有效 ID 和证据，返回根因确定性、推荐修复与可开始的工作。
