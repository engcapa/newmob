# Taomni Issue 修复设计

将问题描述、issue、日志或失败测试转成可实施、可回归、可真机复测的修复设计。默认中文，保留代码标识符原文。核心是复现依据、因果链、准确修复边界及修复前失败/修复后通过的证明。

## 入口与自然语言路由

`prompt`、`design` 是消息中的模式词，不是终端命令；均可省略。

| 请求 | 行为 | 读取资源 |
|---|---|---|
| `$issue-design prompt [问题描述]`，或“帮我生成这个问题的修复设计提示词” | 输出可复制的定制提示词 | [提示词范本](references/prompt-template.md) |
| `$issue-design design <问题、issue 或已有修复设计>`，或“为这个 bug 设计修复方案”“细化这份修复文档” | 调研问题并落盘详细修复设计 | [设计工作流](references/detailed-design.md)、[文档模板](assets/design-document.md)；写验证部分时读取[验证设计](references/verification.md) |

未写模式但提供具体问题时默认 `design`；明确要求提示词或范本时优先 `prompt`。只调用 skill 而没有问题时给可填范本。按实际目标区分问题修复与新增需求，不因资料含 issue 编号就当作 bug。

`prompt` 返回提示词后结束，不执行其中的设计任务。`design` 默认交付文档；用户同时要求实现或验证时继续已授权工作，不额外设置设计审批关卡。

## 固定前提

- 读取当前 Taomni 工程适用 `AGENTS.md`，使用工程相对路径。
- 固定兼容 Windows、macOS、Linux 三端 Tauri 桌面构建与运行，提示词不提供平台或 desktop/browser 选项。问题发生系统只是复现信息，不能缩减代码兼容范围；浏览器用于辅助开发测试。
- 真机计划覆盖三端，本轮完成当前运行端验证即可。其他端未执行记录未验证与后续步骤，不因缺少设备阻塞本轮交付。其他端已知编译或运行缺陷仍须修复，当前端通过不能冒充三端实测通过。
- 区分已复现事实、源码事实、根因推断与待验证假设。无法复现时记录最小区分性检查和缺失环境，不将假设写成确定根因。
- 修复应对应因果链，保留正常行为和兼容契约；不借修复扩展无关需求。普通实现决定由 agent 完成；修复中的实质取舍按下节邀请用户参与，根因明确也不代表修复取舍已经确定。

## 设计中的人工决策

先核对当前会话、已有设计中的有效决定和明确的代决授权。已确定的偏好直接沿用；用户明确要求 agent 自行决定时，在授权范围内选择并记录理由。只有新证据使原决定不再适用或超出授权边界时，才说明变化并重新提出。

调研中主动识别以下取舍。存在多个合理方向，且既有契约、用户要求或技术证据不能确定取舍时，在细化依赖它的修复前邀请用户决策：

| 决策类型 | 需要人工参与的情况 |
|---|---|
| 预期行为与 UI/UX | 预期行为有冲突或缺少权威依据，或修复需要改变操作流程、默认值、错误反馈、重试/恢复方式，且不同选择影响用户体验。 |
| 组件与技术选型 | 修复需引入或替换组件/依赖，候选在交互能力、可访问性、性能、包体、许可证、长期维护或替换成本上存在明显取舍。先由 agent 核实候选是否满足三端及现有架构约束。 |
| 修复边界与兼容代价 | 恢复行为与保留旧数据/接口不能兼得，或临时缓解与完整修复在剩余风险、影响范围、迁移代价和交付成本上需要明确优先级。 |

根因由复现、代码和验证证据判断，不让用户投票选根因。恢复已有契约的局部修复、体验不变的实现细节由 agent 自主处理；存在多个内部实现不自动需要人工选择。缺少技术事实时先安排最小区分性检查，没有实质取舍时无需凑选项或固定提问轮数。

预期行为的分歧尽早提出，不能把自行假定的期望写成已证实的 bug；修复取舍先准备与因果链对应的候选，再在固定回归契约和任务依赖前提出。后续证据引入新取舍时再次判断，不把全部问题留到文档末尾。

每轮聚焦当前最影响后续工作的少量决策（通常 1–3 个）：说明事实与不确定性、为何需要用户判断、通常 2–3 个可行选项、各自恢复/改变的行为与剩余风险、成本、推荐项与理由，以及影响的范围。UI/UX 按下节展示原型与示意图；组件选型比较能力与成本，不只列库名。支持用户提出替代方案，不用泛泛的“是否确认设计”代替具体选择。

按当前环境允许的交互方式实际提出问题；支持异步提问时可边等回复边推进独立诊断和设计，不能只在文档里列“待确认”。需要用户决定的部分可写条件性草案，依赖任务保持待决；未回复、超时或推荐项被预选都不代表同意。收到答复后更新相关行为、契约、AC、TASK 和 V；用户明确授权代决时按其边界收敛。没有可继续的独立工作时，交付已完成部分并明确待决问题及受影响任务。

在设计内用稳定 `DEC-*` 记录有实质影响的决定：问题、选项与代价、结论、理由、状态（用户已定 / 授权代决 / agent 自决 / 待用户决策）、来源（用户答复摘要、授权范围或代码依据）及关联 AC/TASK/V。用户选择预期行为不证明根因成立，也不证明回归已通过；修订保留原 ID 和变更原因。这是按需参与设计，不新增逐步审批或文档最终审批关卡。

### 原型与示意图的交互决策

原型/示意图本身也是需要用户反馈的设计对象。修复涉及布局、信息结构、主要流程或错误恢复交互的实质变化，或用户要求看原型时，在 UI 修复方案定稿前提供可查看的图稿或原型并邀请用户针对它决策；仅恢复已明确界面行为的局部修复不强制重做原型。已有图稿决定和明确代决授权仍按上述规则沿用。

先用低成本示意图、线框或交互原型展示原问题所在状态、修复后布局/行为和必要的恢复分支；有实质备选时提供可比较的版本。明确区分当前实现的真实截图与拟议修复图，不能把模拟图当复现证据。静态图不足以判断交互时，再补最小可交互原型。示意图按当前环境可用的 `drawio` skill 生成，提供可编辑产物和可直接查看的预览；工具不可用时采用可用的本地可视化方式并说明局限，不能把只有文字描述当作已交付图稿。

实际展示图像或可访问的原型链接，标明方案/版本、关键状态及适用窗口尺寸，先检查渲染、可读性和明显遮挡。围绕图稿中的错误提示位置、重试方式、退出后的状态等具体选择提问，附推荐、兼容影响和剩余风险；不要只在文档附图后结束。根据反馈修订并展示差异；影响原有决定的实质变化再次邀请用户判断，普通细节修订自主完成。

在 `DEC-*` 关联图稿路径/版本、反馈摘要、采纳或未采纳理由、最终选择或待决状态。图稿默认放在 `docs-issue/<issue-id-or-slug>/`，文档用相对链接引用并标清当前有效版本；图稿、文字、修复契约和 AC/TASK/V 保持一致。图稿生成、截图成功或用户选择均不证明根因、修复实现或回归验证已完成。

## 文档位置与交接

默认输出工程根目录 `docs-issue/<issue-id-or-slug>-design.md`，目录不存在时创建。同名文档先读后复用或采用更明确的名称。

细化 `docs-issue/` 中的文档时原位更新，保留有效 ID、结论和证据。输入文档在其他目录时默认作为资料，在 `docs-issue/` 产出并记录来源，保留原文；用户明确指定其他输出位置时遵从。不要批量迁移历史文档。

用稳定 `AC-*`、`TASK-*`、`V-*` 串联预期行为、修复方案、改动文件、工作包、回归与证据。任务须明确职责、依赖、具体修改和完成条件，包含集成、相邻功能回归和当前端真机复测责任。拆任务不自动授权启动多个 agent 或修改共享看板。

设计“可实施”与实现、验证状态分开；根因未定时可交付诊断任务及条件性修复方案，明确仅哪些任务受阻。未执行测试标为待执行，已做的复现另记环境、命令和真实结果。

最终返回文档路径、主要根因结论及确定性、推荐修复、关键决策状态、可开始的任务和确实存在的阻塞。文档应让下游无需聊天历史或本 skill 即可执行。
